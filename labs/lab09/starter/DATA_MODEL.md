# Campus Service Request — แบบจำลองข้อมูล

## 1. ภาพรวมและความสัมพันธ์

```text
users                                  requests
┌───────────────────────┐             ┌────────────────────────┐
│ id           PK       │  1       N  │ id             PK      │
│ name                  │◄────────────│ requester_id  FK       │
│ department            │             │ request_type           │
│ email        UNIQUE   │             │ location, details      │
└───────────────────────┘             │ priority, status       │
                                      │ created_at             │
                                      └────────────────────────┘
```

ผู้ใช้หนึ่งคนแจ้งคำร้องได้หลายรายการ (one-to-many) ส่วนคำร้องแต่ละรายการมีผู้แจ้งหนึ่งคน ความสัมพันธ์บังคับด้วย `requests.requester_id` ซึ่งอ้างถึง `users.id` ผ่าน foreign key

## 2. ทำไมต้องแยกเป็น 2 ตาราง

ถ้าเก็บ `requesterName` เป็นข้อความซ้ำในทุกคำร้องเหมือนข้อมูลที่ API เคยส่งใน Week 06–07 จะเกิดปัญหา:

1. **ข้อมูลซ้ำ:** ชื่อและภาควิชาถูกเก็บซ้ำทุกครั้งที่คนเดิมแจ้งคำร้อง ทำให้แก้ไขและสำรองข้อมูลสิ้นเปลือง
2. **แก้ไม่ครบ (update anomaly):** ถ้าสมชายเปลี่ยนชื่อ ต้องไล่แก้ทุกแถวที่มีชื่อเดิม หากพลาดจะมีหลายชื่อแทนคนเดียวกัน; ในแบบจำลองนี้แก้ `users.name` เพียงแถวเดียว
3. **ข้อมูลไม่สอดคล้อง/พิมพ์ผิด:** การสะกดชื่อหรือภาควิชาต่างกันเล็กน้อยทำให้ระบบคิดว่าเป็นคนละคน และไม่มี key ยืนยันตัวตน
4. **เพิ่มผู้ใช้ลำบาก:** หากยังไม่มีคำร้อง ก็ไม่มีแถวคำร้องให้ใช้เก็บข้อมูลผู้ใช้ได้

การแยกตารางเก็บข้อมูลประจำตัวไว้ที่ `users` และเก็บเฉพาะ `requester_id` ใน `requests` ลดความซ้ำซ้อน ขณะที่ foreign key ป้องกันการอ้างถึงผู้ใช้ที่ไม่มีอยู่

## 3. รายละเอียดตารางและเหตุผล

### `users`

| คอลัมน์ | ชนิด | ข้อกำหนด | เหตุผล |
|---|---|---|---|
| `id` | INTEGER | PRIMARY KEY AUTOINCREMENT | รหัสภายในสั้นและสร้างอัตโนมัติ ใช้เชื่อมโยงได้แม้ชื่อหรืออีเมลเปลี่ยน |
| `name` | TEXT | NOT NULL, ห้ามเป็นช่องว่าง | ชื่อเป็นข้อความและจำเป็นต่อการระบุตัวผู้แจ้ง |
| `department` | TEXT | NOT NULL, ห้ามเป็นช่องว่าง | ใช้กรองและสรุปคำร้องตามหน่วยงาน |
| `email` | TEXT | NOT NULL, UNIQUE, ห้ามเป็นช่องว่าง | ใช้ระบุบัญชีผู้ใช้ได้ไม่ซ้ำและป้องกันข้อมูลซ้ำโดยไม่ตั้งใจ |

### `requests`

| คอลัมน์ | ชนิด | ข้อกำหนด | เหตุผล |
|---|---|---|---|
| `id` | TEXT | PRIMARY KEY, ห้ามเป็นช่องว่าง | รหัสอ่านรู้เรื่อง เช่น `REQ-001` เหมาะกับการแสดงผลและอ้างอิงในงานบริการ |
| `requester_id` | INTEGER | NOT NULL, FOREIGN KEY → `users(id)` | ชนิดต้องตรงกับ key ที่อ้างถึง และทุกคำร้องต้องมีผู้แจ้งที่มีจริง |
| `request_type` | TEXT | NOT NULL, CHECK ในชุดประเภทที่กำหนด | ประเภทเป็นข้อความภาษาไทย แต่อยู่ในชุดค่าที่ระบบรองรับ |
| `location` | TEXT | NOT NULL, ห้ามเป็นช่องว่าง | เจ้าหน้าที่ต้องทราบตำแหน่งเพื่อดำเนินการ |
| `details` | TEXT | NOT NULL, ห้ามเป็นช่องว่าง | บันทึกรายละเอียดที่ช่วยให้เข้าใจคำร้อง |
| `priority` | TEXT | NOT NULL, DEFAULT `normal`, CHECK `normal`/`urgent` | มีค่าปริยายที่ปลอดภัยและจำกัดระดับความเร่งด่วน |
| `status` | TEXT | NOT NULL, DEFAULT `pending`, CHECK `pending`/`in-progress`/`completed` | ให้สถานะเริ่มต้นชัดเจนและป้องกันสถานะสะกดผิด |
| `created_at` | TEXT | NOT NULL, DEFAULT เวลาปัจจุบัน | เก็บเวลาในรูปแบบ SQLite ที่เรียงลำดับตามเวลาได้ |

`users.id` เป็น INTEGER เพราะเป็น surrogate key ภายในและ SQLite สร้างเลขต่อเนื่องให้ ส่วน `requests.id` เป็น TEXT เพราะต้องการรหัสธุรกิจที่อ่านและสื่อความหมายได้ เช่น `REQ-001` ทั้งสอง primary key มีหน้าที่เหมือนกันแต่รูปแบบการใช้งานต่างกัน

ถึง API จะตรวจข้อมูล ก็ยังต้องมี `CHECK` ในฐานข้อมูล: ข้อมูลอาจถูกเขียนจากสคริปต์อื่น, เครื่องมือ SQL หรือ endpoint ที่ลืม validation หากมีหลายทางเขียน ฐานข้อมูลเป็นแนวป้องกันชั้นสุดท้ายที่บังคับกติกาเดียวกันทุกทาง

## 4. ตัวอย่าง JOIN และผลลัพธ์

```sql
SELECT r.id, u.name AS requester_name, r.status
FROM requests AS r
JOIN users AS u ON u.id = r.requester_id
WHERE r.id IN ('REQ-001', 'REQ-002', 'REQ-003')
ORDER BY r.id;
```

ผลจาก sample data:

| id | requester_name | status |
|---|---|---|
| REQ-001 | สมชาย ใจดี | pending |
| REQ-002 | สุภาวดี รักเรียน | in-progress |
| REQ-003 | ธนกฤต ตั้งใจ | completed |

## 5. ผลการทดสอบ constraint

การทดสอบเชิงปฏิบัติอยู่ใน [`CONSTRAINT_TEST.md`](CONSTRAINT_TEST.md) และรันซ้ำได้ด้วย `node validate.mjs` โดยเปิด foreign keys และยืนยันว่า invalid foreign key, status ที่ไม่อยู่ใน CHECK, อีเมลซ้ำ, id ซ้ำ และ location ที่หายไป ล้วนถูกปฏิเสธจริง

## 6. ข้อสังเกตสำหรับสัปดาห์ที่ 10

JOIN คืนข้อมูลเชิงสัมพันธ์จากตารางที่แยกกัน แต่ API ของ Week 07 ส่ง object แบบแบนให้ React เช่น `{ "id": "REQ-001", "requesterName": "สมชาย ใจดี", "status": "pending" }` ดังนั้น service layer สามารถใช้ JOIN แล้ว map alias `requester_name` เป็น `requesterName` ได้ โดยไม่ต้องเปลี่ยนรูปแบบข้อมูลที่หน้าจอใช้อยู่ การแยกในฐานข้อมูลไม่ได้บังคับให้ frontend ต้องรับ object ซ้อนกัน
